Planner — Gestor de Agenda

Guía de estructura del repositorio, reglas del equipo y proceso para subir una rama feature/

Programa: SENA · Formación en desarrollo de software
Stack: Flutter (Android + Web) · Clean Architecture
Backend: Neon (PostgreSQL Serverless) + API REST
Metodología: GitFlow con Pull Requests
Equipo: 5 aprendices con roles definidos
Versión: 1.1 · Noviembre de 2026

1. Objetivo del documento

Este documento reúne las tres reglas de trabajo que el equipo debe respetar para que el proyecto Planner sea evaluable y mantenible: (1) cómo está organizado el repositorio y sus carpetas, (2) qué reglas del repositorio están activas, y (3) el proceso paso a paso para subir una parte del proyecto en una rama feature/<nombre-de-la-rama>.

Está dirigido a los cinco integrantes y al instructor que evalúa. Cualquier integrante debe poder tomar una tarea, crear su rama, subir el trabajo y conseguir que se integre a develop sin depender de otra persona.

Regla de oro: nada llega a main ni a develop por push directo. Todo cambio entra por Pull Request revisado y aprobado por dos compañeros, uno de ellos el Tech Lead.

Al ejecutar flutter create --platforms=android,web . se sumarán las carpetas android/, web/, test/ y el archivo pubspec.yaml.

2.3 Qué se escribe en cada carpeta

CarpetaContenidoRegla de dependencia
core/constantsURL base de la API, rutas internas, claves públicas.Puede usarse desde cualquier capa.
core/errorsExcepciones propias y modelos de Failure.Sin dependencias de Flutter.
core/networkCliente Dio/http, interceptores, estado de conexión.Lo usa solo la capa data.
core/utilsFormateo de fechas (intl), validadores de formularios.Sin dependencias de UI.
data/datasourcesLlamadas HTTP a la API y, si aplica, caché local.Implementa lo que exige el dominio.
data/modelsClases con fromJson / toJson y mapeo a entidades.Depende de domain/entities.
data/repositoriesImplementación concreta del contrato del dominio.Implementa domain/repositories.
domain/entitiesEvento, Categoria: objetos puros e inmutables.No importa Flutter, Dio ni la base de datos.
domain/repositoriesInterfaces abstractas (PlannerRepository).No conoce implementaciones.
domain/usecasesCrearEvento, ListarEventos, ActualizarEvento, EliminarEvento.Orquesta entidades y contratos.
presentation/blocEventos, estados y Bloc del feature.Llama casos de uso, nunca datasources.
presentation/pagesPantallas completas conectadas al Bloc.Depende de bloc y widgets.
presentation/widgetsCalendario, tarjetas de evento, inputs y tema visual.Widgets sin lógica de negocio.
Dirección de las dependencias: presentation conoce a domain; data implementa a domain; domain no conoce a nadie. Si una entidad necesita importar Flutter o Dio, está mal diseñada.

3. Reglas del repositorio

3.1 Ramas y nivel de protección

RamaProtegidaUso
mainSí (máxima)Solo recibe merges desde release/vX.0. Cada merge se etiqueta (v1.0.0).
developSíIntegración diaria. Recibe los PR de las ramas feature/.
release/vX.0Sí (release/*)Pruebas de integración antes de pasar a main.
feature/<nombre>NoTrabajo individual. Nace de develop y muere al fusionarse.

3.2 Las cuatro reglas obligatorias del taller

#ReglaCómo se garantiza técnicamente
1 Prohibido el push directo a main y develop. Ruleset activo con Require a pull request before merging, Restrict deletions y Block force pushes.
2 Toda funcionalidad nace de develop como feature/nombre-tarea. Todo PR de una rama feature/ apunta a develop; solo release/* apunta a main.
3 PR aprobado por al menos 2 compañeros, incluido el Tech Lead. Required approvals: 2 + Require review from Code Owners con el Tech Lead en CODEOWNERS.
4 Al cerrar una fase se crea release/vX.0, se prueba y se fusiona a main con etiqueta git tag v1.0.0. Rama release/* protegida + tag creado desde la release (idealmente protegido con el patrón v*).
Alcance de este documento: la configuración técnica de las protecciones la realiza el Tech Lead una sola vez. Aquí solo se describen las reglas que aplican al equipo y la forma de trabajar dentro de ellas.

4. Proceso para subir una rama con una parte del proyecto

Cada integrante trabaja una tarea por rama, siempre creada desde develop y con el prefijo feature/. La rama se sube al remoto, se abre un Pull Request hacia develop, se consiguen las dos aprobaciones y se fusiona. La rama se elimina al finalizar.

1. developActualizar
→
2. feature/Crear rama
→
3. CódigoImplementar
→
4. PushSubir rama
→
5. PRHacia develop
→
6. Review2 aprobaciones
→
7. Merge+ borrar rama

4.1 Nomenclatura obligatoria de las ramas

Formato: feature/<nombre-de-la-rama>. El nombre describe la tarea en minúsculas, sin espacios, separando palabras con guiones (kebab-case) y sin acentos ni ñ. Una rama no mezcla dos responsabilidades.

RamaResponsableContenido que monta
feature/neon-datasourceBackend & DataDatasource remoto, modelos con fromJson/toJson e implementación del repositorio.
feature/domain-layerDomain ArchitectEntidades Evento y Categoria, contrato del repositorio y casos de uso.
feature/ui-componentsUI/UXTema visual, calendario interactivo y tarjetas de evento.
feature/presentation-logicState & IntegrationBloc, pantallas e inyección de dependencias con get_it.
feature/auth-loginCualquieraEjemplo de tarea puntual posterior: pantalla de inicio de sesión.
fix/error-fecha-eventoCualquieraCorrección de un error (prefijo fix/ para bugs).

Prohibidos: feature/Domain Layer, feature/dominio de forma ambigua, mi-rama, prueba, cambios. El nombre debe permitir saber qué contiene sin abrir el PR.

4.2 Paso a paso para subir la rama

Paso 0 · Preparación (una sola vez por integrante)

git clone https://github.com/<organizacion>/<repositorio>.git
cd Actividad-8flutter
git checkout develop
flutter pub get

Paso 1 · Sincronizar develop antes de empezar

git checkout develop
git pull origin develop

Si no sincronizas, tu rama nace desactualizada y el PR generará conflictos.

Paso 2 · Crear la rama de la tarea

git checkout -b feature/domain-layer

Paso 3 · Implementar solo lo que corresponde a la rama

RamaCarpetas que debe tocar
feature/domain-layerlib/features/planner/domain/entities, repositories y usecases
feature/neon-datasourcelib/features/planner/data/* y lib/core/network
feature/ui-componentslib/features/planner/presentation/widgets y el tema en lib/core/utils
feature/presentation-logicpresentation/bloc, presentation/pages y el registro de get_it
Una rama = una responsabilidad. Si estás en feature/domain-layer no modifiques data/ ni presentation/: eso pertenece a otra rama y a otro integrante. Si lo necesitas, coordina con el Tech Lead.

Paso 4 · Revisar el código y hacer commits pequeños

flutter analyze          # no debe reportar errores
git status
git add lib/features/planner/domain/
git commit -m "feat(domain): agrega entidades Evento y Categoria"

Formato de commit: tipo(alcance): descripción en imperativo. Tipos válidos: feat, fix, docs, refactor, test, chore.

Paso 5 · Subir la rama al repositorio remoto

git push -u origin feature/domain-layer

El -u deja la rama enlazada: los siguientes git push funcionan sin argumentos. El push a feature/* sí está permitido; a main y develop, no.

Paso 6 · Abrir el Pull Request hacia develop

  1. Entrar al repositorio y pulsar el aviso Compare & pull request (o Pull requests → New pull request).
  2. Verificar las ramas: base: develop ← compare: feature/domain-layer. Si la base aparece como main, cambiarla.
  3. Título claro, por ejemplo: feat(domain): entidades y casos de uso de eventos.
  4. Completar la descripción: qué se hizo, qué carpetas se tocaron, cómo probarlo y qué issue cierra (Closes #12).
  5. Asignar revisores: el Tech Lead y al menos otro compañero.

Paso 7 · Revisión y correcciones

  • Los revisores comentan en Files changed; el autor responde y corrige con nuevos commits (no se abre otro PR).
  • Cada commit nuevo descarta las aprobaciones anteriores (regla configurada), así que se aprueba al final.
  • Se necesitan 2 aprobaciones, una de ellas del Tech Lead vía CODEOWNERS, y todas las conversaciones resueltas.

Paso 8 · Fusionar el PR

Cuando el botón se habilite, usar Squash and merge si el equipo adoptó historial limpio. Tras el merge, pulsar Delete branch (GitHub también puede hacerlo automático si el Tech Lead activó Automatically delete head branches).

Paso 9 · Actualizar el entorno local

git checkout develop
git pull origin develop
git branch -d feature/domain-layer
git fetch --prune

4.3 Lista de verificación antes de abrir el PR

✔Comprobación
☐La rama se creó desde develop actualizado y se llama feature/<nombre>.
☐Solo contiene cambios de esa responsabilidad (no hay archivos de otras capas).
☐flutter analyze termina sin errores.
☐No se subieron .env, llaves ni archivos de build/.
☐Los commits siguen la convención y están en imperativo.
☐El PR apunta a develop, tiene título y descripción completos.
☐Están asignados los revisores (Tech Lead + un compañero).

4.4 Errores frecuentes y cómo resolverlos

SíntomaCausaSolución
GH006: Protected branch update failed Intentaste hacer push directo a develop o main. Crear la rama feature/…, subir allí y abrir el PR.
! [rejected] … (fetch first) El remoto tiene commits que no tienes localmente. git pull --rebase origin <rama>. Nunca usar --force en ramas compartidas.
El PR muestra “This branch has conflicts” Otra rama tocó las mismas líneas en develop. Traer develop a la rama: git checkout feature/…, git pull --rebase origin develop, resolver, commit y push.
El botón Merge sigue bloqueado con 2 aprobaciones Falta la aprobación del Code Owner o hay conversaciones abiertas. Pedir revisión al Tech Lead y resolver cada comentario (Resolve conversation).
“Dismissed stale review” tras un commit nuevo Se subió código después de aprobar. Volver a solicitar revisión; es el comportamiento correcto.
El PR aparece hacia main La rama base por defecto del repositorio es main. Editar el PR y cambiar la base a develop (Edit → base).

4.5 Si ya hiciste commits en la rama equivocada

# Mover los commits de develop a una rama nueva, sin perder trabajo
git checkout develop
git branch feature/mi-tarea            # guarda los commits en la rama nueva
git reset --hard origin/develop        # develop vuelve al estado remoto
git checkout feature/mi-tarea
Precaución: git reset --hard borra cambios locales no confirmados. Úsalo solo cuando los commits ya estén seguros en otra rama.
